# 每日打卡、物种讨论与积分商城实现方案

本文说明三项功能如何接到现有系统上：小程序识别成功后写入 Redis 做当日打卡排行，同一物种当日打卡用户进入讨论 Feed，积分可在商城兑换，特价商品用 Redisson 锁避免超卖。

## 1. 现状与边界

当前后端是 Spring Boot 4.0.6、Java 17、MyBatis-Plus、MySQL（库名 `animal-recognition`）。登录态由 `JwtTokenUserInterceptor` 保护，放行路径只有 `/user/login` 和 `/open/**`。小程序识别结果通过 `POST /open/recognition-records` 落入 `recognition_record`。`species`、`user` 已存在。项目里还没有 Redis，`pages/checkin` 仍是空页面。

三项功能都依赖登录用户，不能挂在 `/open/**` 上。识别记录继续走现有开放接口；打卡、讨论、兑换走需要 Token 的用户接口，用户 ID 从 `BaseContext` 取，不信任请求体里的 `userId`。

Redis 负责当日排行、去重和 Feed 索引。积分余额、评论正文、商品库存、兑换订单以 MySQL 为准。Redis 重启或过期后，排行可以没有，账和订单不能丢。

业务上的「当天」使用 `Asia/Shanghai`，格式 `yyyyMMdd`。数据源 URL 里的 `serverTimezone=UTC` 只影响 JDBC 时间解释，不能拿来切日。

## 2. 技术栈

在 `elephantJava/pom.xml` 增加：

| 组件 | 用途 |
| --- | --- |
| `spring-boot-starter-data-redis` | `StringRedisTemplate` 操作 SET、ZSET、Hash。版本跟随 Spring Boot 4.0.6 |
| `org.redisson:redisson-spring-boot-starter` | 只用于特价商品分布式锁。版本取 Maven Central 上兼容 Spring Boot 4 的最新稳定版 |

Redis 使用本机 `localhost:6379`，数据库 0。两个客户端连同一个实例：数据结构用 Lettuce（Spring Data Redis），锁用 Redisson。

`application.yaml` 增加：

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      database: 0
      timeout: 3s
```

小程序继续用现有请求封装，Header 带 `token`。管理端 `elephantVue` 只增加商品维护和订单查询，不参与打卡写入。

## 3. 功能一：每日物种打卡与积分

### 3.1 规则

- 一次有效打卡：同一用户、同一物种、同一个自然日只计一次。重复识别仍保存 `recognition_record`，不再改名次、不再加积分。
- 排行范围：某一个物种的当天打卡用户。
- 排序分值：打卡时刻的毫秒时间戳，越小越早。`ZRANGE` 下标 0 是第 1 名。
- 积分只在首次打卡时发放，名次越高积分越高，之后名次变化不追补、不扣回。

建议积分表（可做成配置，先写死在服务里）：

| 名次 | 积分 |
| --- | --- |
| 1 | 50 |
| 2 | 30 |
| 3 | 20 |
| 4～10 | 10 |
| 11 及以后 | 5 |

同一毫秒并列时，Redis 按 member 字典序打破平局。member 使用用户 ID 的十进制字符串。

### 3.2 Redis 数据结构

`{date}` 为上海时区日期，例如 `20261013`。两个 key 使用同一个过期时间：当日 24:00 后再保留 48 小时，便于跨天查看昨天的榜，之后自动删除。

| Key | 类型 | member / field | score | 含义 |
| --- | --- | --- | --- | --- |
| `checkin:users:{speciesId}:{date}` | SET | `userId` | — | 当天该物种已打卡用户，用于去重，也是讨论模块的接收人集合 |
| `checkin:rank:{speciesId}:{date}` | ZSET | `userId` | 打卡毫秒时间戳 | 当天该物种打卡排行 |
| `checkin:species:{userId}:{date}` | SET | `speciesId` | — | 该用户当天打过卡的物种，用于「我的打卡」 |

展示昵称、头像、物种名不放进 ZSET。排行接口用 ZSET 取出 userId 后，回表查 `user`、`species`。

### 3.3 写入必须原子

先 `SISMEMBER` 再 `SADD`/`ZADD` 会在并发下双计。用一条 Lua 完成判断、写入和取名次：

```lua
-- KEYS[1] 打卡用户 SET
-- KEYS[2] 排行 ZSET
-- KEYS[3] 用户当日物种 SET
-- ARGV[1] userId  ARGV[2] score(毫秒)  ARGV[3] speciesId  ARGV[4] expireAt(unix秒)
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then
  return -1
end
redis.call('SADD', KEYS[1], ARGV[1])
redis.call('ZADD', KEYS[2], ARGV[2], ARGV[1])
redis.call('SADD', KEYS[3], ARGV[3])
if redis.call('TTL', KEYS[1]) < 0 then
  redis.call('EXPIREAT', KEYS[1], ARGV[4])
  redis.call('EXPIREAT', KEYS[2], ARGV[4])
  redis.call('EXPIREAT', KEYS[3], ARGV[4])
end
return redis.call('ZRANK', KEYS[2], ARGV[1])
```

返回值 `-1` 表示今日已打卡；`0` 表示第 1 名。Java 侧名次 = 返回值 + 1，再查积分表。

`StringRedisTemplate.execute(RedisScript)` 调用这段脚本。脚本随服务发版，不手写到 Redis。

### 3.4 MySQL

```sql
ALTER TABLE user
  ADD COLUMN points INT NOT NULL DEFAULT 0 COMMENT '当前积分';

CREATE TABLE point_log (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id       BIGINT       NOT NULL,
  change_amount INT          NOT NULL COMMENT '正数为获得，负数为消耗',
  balance_after INT          NOT NULL,
  biz_type      VARCHAR(32)  NOT NULL COMMENT 'CHECKIN / EXCHANGE',
  biz_id        VARCHAR(64)  NOT NULL COMMENT '打卡为 speciesId:yyyyMMdd，兑换为订单号',
  remark        VARCHAR(255) NULL,
  create_time   DATETIME     NOT NULL,
  UNIQUE KEY uk_biz (user_id, biz_type, biz_id),
  KEY idx_user_time (user_id, create_time)
) COMMENT '积分流水';
```

`points` 是余额缓存，`point_log` 是账本。`uk_biz` 保证同一天同一物种只会入账一次。发放积分使用：

```sql
UPDATE user SET points = points + #{amount} WHERE id = #{userId};
INSERT INTO point_log (...) VALUES (...);
```

两句放在同一个 `@Transactional` 里。若 Lua 已写入 Redis 但数据库事务失败，捕获唯一键冲突视为已入账；其他失败记错误日志，由补偿任务按 `checkin:rank` 与 `point_log` 对账补发。不在 Redis 成功后把 SET member 删掉再重试，避免名次被后来的人占走又发两份积分。

打卡流水 `biz_id` 格式：`{speciesId}:{yyyyMMdd}`。

### 3.5 接口与调用时机

小程序在 `pages/elephant/elephant.js` 里，现有 `POST /open/recognition-records` 返回成功且能对应到 `species.id` 之后，再调用打卡接口。物种匹配用识别结果 `predictedName` 对 `species.name`（或 `species.code`）。对不上则只保留识别记录，不打卡。

`POST /user/checkins`

请求：

```json
{
  "speciesId": 1,
  "recognitionRecordId": 128
}
```

响应 `data`：

```json
{
  "firstCheckin": true,
  "rank": 3,
  "pointsAwarded": 20,
  "pointsBalance": 120,
  "checkinTime": 1760342400123
}
```

重复打卡时 `firstCheckin=false`，`pointsAwarded=0`，`rank` 仍返回当日名次。

`GET /user/checkins/rank?speciesId=1&date=20261013`

`date` 缺省为今天。响应：

```json
{
  "speciesId": 1,
  "speciesName": "亚洲象",
  "date": "20261013",
  "total": 36,
  "myRank": 3,
  "myPointsAwarded": 20,
  "list": [
    {
      "rank": 1,
      "userId": 8,
      "realName": "林晓",
      "checkinTime": 1760342100000,
      "pointsAwarded": 50
    }
  ]
}
```

读路径：`ZCARD` 得总数，`ZRANGE key 0 49 WITHSCORES` 取前 50，`ZRANK` 取我的名次。积分按名次用同一张表重算，不另存一份排行积分，避免和规则不一致。

`GET /user/points` 返回 `{ "points": 120 }`。

### 3.6 小程序页面

`pages/checkin/checkin` 展示当天可选物种、该物种排行、我的名次和积分。识别结果页在打卡成功后把 `rank`、`pointsAwarded` 展示出来，并提供进入排行页的入口。

## 4. 功能二：物种当日讨论 Feed

### 4.1 谁能看、谁能发

用户当天对某物种首次打卡成功后，已经在 `checkin:users:{speciesId}:{date}` 里。这个 SET 就是该物种当天的消息接收人集合，不再建第二份名单。

发布和查询前都执行 `SISMEMBER`。不在集合中返回业务错误：「请先完成该物种今日打卡」。集合随打卡 key 一起过期，次日需要重新打卡才能进入新的一天的讨论。

讨论内容按物种、按天隔离。今天打卡亚洲象的人看不到昨天的亚洲象评论，也看不到今天其他物种的评论。

### 4.2 数据格式

评论正文放 MySQL，时间线索引放 ZSET。ZSET 只存评论 ID，便于按时间翻页；正文不塞进 member，避免大 value 和修改困难。

```sql
CREATE TABLE species_comment (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  species_id   BIGINT       NOT NULL,
  user_id      BIGINT       NOT NULL,
  biz_date     CHAR(8)      NOT NULL COMMENT '上海时区 yyyyMMdd',
  content      VARCHAR(500) NOT NULL,
  create_time  DATETIME(3)  NOT NULL,
  KEY idx_feed (species_id, biz_date, create_time, id)
) COMMENT '物种当日讨论';
```

| Key | 类型 | member | score |
| --- | --- | --- | --- |
| `feed:timeline:{speciesId}:{date}` | ZSET | `commentId` | 评论创建时间的毫秒时间戳 |

过期时间与打卡 key 相同。

这是读扩散：一条评论只写一次时间线，接收人读同一条 ZSET。打卡规模远小于需要给每个用户扇出一份收件箱的场景，不把评论复制进 `feed:inbox:{userId}`。接收人集合已经表达「谁可以收到这个物种的消息」。

### 4.3 发布

`POST /user/feeds/{speciesId}/comments`

```json
{ "content": "今天在保护区西侧看到一只亚成体。" }
```

处理顺序：

1. 校验内容非空，最长 500 字。
2. `SISMEMBER checkin:users:{speciesId}:{today}`，不在则拒绝。
3. 插入 `species_comment`，`create_time` 用上海时区当前时间，精度到毫秒。
4. `ZADD feed:timeline:{speciesId}:{today} score commentId`，并为时间线设置与打卡相同的 `EXPIREAT`。
5. 返回完整评论对象。

第 4 步失败时评论已在 MySQL。查询端在 Redis 时间线缺失时回退到 MySQL，不要求发布接口做跨存储分布式事务。

响应：

```json
{
  "id": 9001,
  "speciesId": 1,
  "userId": 8,
  "realName": "林晓",
  "content": "今天在保护区西侧看到一只亚成体。",
  "createTime": 1760342500456
}
```

### 4.4 按时间戳滚动查询

`GET /user/feeds/{speciesId}/comments?cursor=&size=10`

- 不传 `cursor`：取最新一页。
- 传入上一页最后一条的 `createTime`：取严格早于该时间的下一页。
- `size` 默认 10，最大 20。

Redis 命令使用开区间，避免边界重复：

```text
ZREVRANGEBYSCORE feed:timeline:{speciesId}:{date} ( {cursor} +inf LIMIT 0 {size}
```

首次加载把 `{cursor}` 换成 `+inf`，不加 `(`。

得到 commentId 列表后 `WHERE id IN (...)` 批量查评论，再按 ZSET 返回顺序排列，并补 `realName`。

Redis key 不存在或结果为空时，回退：

```sql
SELECT * FROM species_comment
WHERE species_id = #{speciesId}
  AND biz_date = #{date}
  AND create_time < #{cursorTime}   -- 首次加载去掉此条件
ORDER BY create_time DESC, id DESC
LIMIT #{size}
```

响应：

```json
{
  "list": [ ],
  "nextCursor": 1760342500456,
  "hasMore": true
}
```

`nextCursor` 取本页最后一条的 `createTime`。本页条数小于 `size` 时 `hasMore=false`，小程序停止上拉。

同一毫秒有多条时，MySQL 回退用 `(create_time, id)` 做游标：`create_time < cursorTime OR (create_time = cursorTime AND id < cursorId)`。Redis 路径若 score 冲突，member 为评论 ID，翻页仍可能把同一毫秒的另一条留在下一页；回退 SQL 用双游标即可。接口同时返回 `nextCursor` 与 `nextCursorId`，Redis 正常时客户端只传 `cursor`。

### 4.5 小程序交互

新页面 `pages/feed/feed`，入口放在打卡排行页，必须带上 `speciesId`。

- 下拉刷新：不带 `cursor`，替换列表。
- 上拉触底：带上当前列表最后一条的 `createTime`，追加到列表尾部。
- 发送框：调用发布接口，成功后插入列表头部，不重新拉全量。

`app.json` 的 `pages` 注册该页面。未打卡用户进入时展示打卡引导，不展示空评论列表冒充「还没有人发言」。

## 5. 功能三：积分商城与特价防超卖

### 5.1 商品模型

普通商品用数据库条件更新扣库存即可。特价商品（限时、低积分、库存少）在扣库存前加 Redisson 锁，把「查库存、扣积分、扣库存、建订单」串行化。

```sql
CREATE TABLE point_goods (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  name           VARCHAR(64)  NOT NULL,
  cover_url      VARCHAR(255) NULL,
  description    VARCHAR(500) NULL,
  points_price   INT          NOT NULL,
  stock          INT          NOT NULL,
  goods_type     VARCHAR(16)  NOT NULL COMMENT 'NORMAL / SPECIAL',
  status         VARCHAR(16)  NOT NULL COMMENT 'ON / OFF',
  limit_per_user INT          NOT NULL DEFAULT 1,
  sale_start     DATETIME     NULL,
  sale_end       DATETIME     NULL,
  create_time    DATETIME     NOT NULL,
  update_time    DATETIME     NOT NULL
) COMMENT '积分商品';

CREATE TABLE point_order (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no      VARCHAR(32)  NOT NULL,
  user_id       BIGINT       NOT NULL,
  goods_id      BIGINT       NOT NULL,
  goods_name    VARCHAR(64)  NOT NULL,
  points_cost   INT          NOT NULL,
  status        VARCHAR(16)  NOT NULL COMMENT 'SUCCESS',
  request_id    VARCHAR(64)  NOT NULL COMMENT '客户端幂等号',
  create_time   DATETIME     NOT NULL,
  UNIQUE KEY uk_request (user_id, request_id),
  KEY idx_user_time (user_id, create_time),
  KEY idx_goods (goods_id)
) COMMENT '积分兑换订单';
```

特价是否开售由 `goods_type=SPECIAL` 加上 `sale_start`、`sale_end` 判断。库存以 `point_goods.stock` 为准，不把库存只放在 Redis。

### 5.2 兑换流程

`POST /user/point-orders`

```json
{
  "goodsId": 3,
  "requestId": "8-3-6f1c0c2e-7b44-4d1a-9a0e-1c2b3d4e5f60"
}
```

`requestId` 由小程序生成，同一次点击重试必须复用。先按 `(user_id, request_id)` 查订单，已存在则直接返回该订单。

处理步骤：

1. 读取商品。下架、未到开售时间、已过结束时间，直接失败。
2. 仅当 `goods_type=SPECIAL` 时获取锁，锁 key 为 `lock:point-goods:{goodsId}`。
3. 在锁内开启数据库事务：
   - 统计该用户对该商品的成功订单数，达到 `limit_per_user` 则失败。
   - 扣积分：`UPDATE user SET points = points - #{price} WHERE id = #{userId} AND points >= #{price}`。影响行数为 0 表示积分不足。
   - 扣库存：`UPDATE point_goods SET stock = stock - 1, update_time = NOW() WHERE id = #{goodsId} AND stock > 0 AND status = 'ON'`。影响行数为 0 表示售罄或已下架。
   - 插入 `point_order`，写入一条 `change_amount` 为负数的 `point_log`，`biz_type=EXCHANGE`，`biz_id=orderNo`。
4. 任一步影响行数不为 1，抛业务异常，事务回滚。
5. `finally` 中仅在当前线程仍持有锁时 `unlock`。

普通商品跳过第 2 步，仍使用第 3 步的条件更新。两条 `UPDATE` 的影响行数判断是最后一道防线，锁失效时也不会把库存扣成负数，也不会把积分扣成负数。

锁的用法：

```java
RLock lock = redissonClient.getLock("lock:point-goods:" + goodsId);
boolean locked = false;
try {
    locked = lock.tryLock(1, TimeUnit.SECONDS);
    if (!locked) {
        throw new BaseException("兑换人数较多，请稍后再试");
    }
    orderService.exchangeInTransaction(userId, goods, requestId);
} finally {
    if (locked && lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

`tryLock(waitTime)` 不传租约时，Redisson 看门狗会给持有锁的线程续期，避免事务还没提交锁就过期。等待只设 1 秒，拿不到就失败，不让请求在锁上堆积。锁按商品 ID 拆分，不同特价商品可以并行兑换。

不要用一把全局锁罩住整个商城，也不要在锁外先扣积分再抢锁。

### 5.3 查询接口

`GET /user/point-goods?type=SPECIAL` 返回在售商品：`id`、`name`、`coverUrl`、`pointsPrice`、`stock`、`goodsType`、`saleStart`、`saleEnd`、`limitPerUser`。库存为 0 仍返回，前端显示已兑完。

`GET /user/point-orders?cursor=&size=10` 用 `create_time` + `id` 做时间戳滚动，规则与评论 Feed 相同。

管理端接口（沿用现有后台 JWT）：

- `POST /point-goods` 新增
- `PUT /point-goods/{id}` 修改价格、库存、上下架、开售窗口
- `GET /point-goods` 分页
- `GET /point-orders` 按商品、用户、时间筛选

改库存和上下架不需要分布式锁。兑换事务里的 `stock > 0 AND status = 'ON'` 会读到最新行。

### 5.4 小程序页面

新页面 `pages/mall/mall`：商品列表、积分余额、兑换按钮。特价商品展示开售倒计时。兑换中按钮置灰。失败文案使用接口 `msg`（积分不足、已兑完、超出限购、请稍后再试）。成功后刷新余额和库存。

## 6. 接口一览

统一响应仍是 `Result`：`code=1` 成功，`code=0` 失败，`msg` 为原因，`data` 为上面的对象。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/user/checkins` | 物种打卡，写 SET/ZSET 并发积分 |
| GET | `/user/checkins/rank` | 当日物种打卡排行 |
| GET | `/user/points` | 积分余额 |
| POST | `/user/feeds/{speciesId}/comments` | 发布当日物种评论 |
| GET | `/user/feeds/{speciesId}/comments` | 按时间戳向更早翻页 |
| GET | `/user/point-goods` | 商城商品 |
| POST | `/user/point-orders` | 兑换 |
| GET | `/user/point-orders` | 我的兑换记录 |

这些路径都走现有 JWT 拦截器。

## 7. 后端类划分

与现有分层保持一致：

| 类 | 职责 |
| --- | --- |
| `RedisConfig` | 声明 `StringRedisTemplate` 已由 starter 自动配置；此处只放 Lua `DefaultRedisScript<Long>` Bean |
| `CheckinServiceImpl` | 执行打卡 Lua、算积分、写 `point_log`、组装排行 |
| `FeedServiceImpl` | 校验接收人 SET、写评论、ZSET 翻页与 MySQL 回退 |
| `PointMallServiceImpl` | 商品查询、加锁、调用事务方法兑换 |
| `PointOrderTxService` | 独立 Bean 上的 `@Transactional` 兑换方法，避免同类自调用导致事务不生效 |
| `CheckinController`、`FeedController`、`PointMallController` | 入参校验与 `Result` 包装 |

业务日期、积分档位、key 前缀放在 `CheckinConstants`，不要散落在各个 Service 里。

## 8. 建议落地顺序

1. 接入 Redis，跑通 Lua 打卡与排行查询，并用唯一键把积分落到 `user.points`。
2. 小程序识别成功后调用打卡，打卡页展示排行。
3. 用同一个 SET 做讨论准入，先完成 MySQL 评论和 `cursor` 翻页，再补 ZSET 索引。
4. 建商品和订单表，先做普通商品条件更新扣库存。
5. 给 `SPECIAL` 商品加上 Redisson 锁，用并发请求验证库存不会小于 0、积分不会小于 0、重复 `requestId` 只有一笔订单。

第 5 步可以用一组并行 HTTP 请求打同一特价商品：库存 5、并发 50。期望成功订单数等于 5，`point_goods.stock` 为 0，失败请求的积分不变。
