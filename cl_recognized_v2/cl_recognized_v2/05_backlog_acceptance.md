# 项目任务清单、开发顺序与验收标准（v2.0）

> **用途**：这一份可以直接导入 GitHub Issues/项目看板来分工。基于源码与 `/docs` 两份方案制定，任务均表示**待实现**。参考周期为 8～10 周（多人并行），不是对实际工期的承诺。不要为了赶进度跳过 P0 鉴权、记账与内容审核。

## 一、启动前：先建立统一开发基线（P0，半天～两天）

| 工单 | 任务与负责人建议 | 交付物/验收 | 依赖 |
| --- | --- | --- | --- |
| B00 | 项目负责人确认 MySQL 版本、JDK 17+ 构建、Redis 版本、微信 appid 和后端部署环境 | 本地启动说明；`/actuator/health` 或自检接口（新增）通过；记录实际版本 | 无 |
| B01 | 后端确认 `individual`、`species`、`recognition_record` 的真实 DDL 与 `entity/` 是否一致 | `schema_baseline.sql`（不含真实隐私/密码）、迁移核对表 | B00 |
| B02 | 视觉模型负责人提供 FastAPI `/predict` 的固定示例、类别清单及置信度含义 | 5 张脱敏样图的识别请求/响应；label → individual 映射表 | B00 |
| B03 | 文档负责人确认原需求积分档位、日界线、讨论审核规则、退款与敏感位置政策 | 产品决策记录（ADR-001） | 无 |
| B04 | 安全负责人清理明文密码/Token 日志、凭据入环境变量，检查 Git 历史 | 安全检查报告；如凭据真实且暴露则轮换 | B00 |

注意：`04_mysql_migration_DRAFT.sql` **仅为迁移评审草稿**。实际跑迁移前必须对照生产表结构、列名/类型/现有数据，先备份、再准备回滚和测试环境。不得直接向正在运行的线上数据库复制执行。

## 二、按里程碑实施（可并行工作包）

| 里程碑 | 本阶段必须完成 | 推荐负责人 | 阶段演示与 DoD（完成标准） |
| --- | --- | --- | --- |
| M0 现状与安全（第 1 周） | B00～B04；员工与游客权限边界；ThreadLocal 清理；图片输入限制 | 后端 + 测试 | 自造匿名识别记录**不能领积分**；日志不含密码与原始 JWT |
| M1 游客身份和可信识别（第 2 周） | `wx.login` → `visitor_user` → Visitor JWT；Java 接收图像、代理 Python；`recognition_job` 生命周期 | Java + 小程序 + 视觉算法 | 真实用户上传后 Java 保存服务端签发的 job；游客只能看自己任务 |
| M2 动物卡片（第 3 周） | 按物种+稳定 code 映射个体；头像/年龄源；`unknown/uncertain`；结果页升级 | Java + 小程序 + 数据维护 | 演示成功、失败、低可信、缺头像、缺年龄 5 条链路；不凭图片瞎猜年龄 |
| M3 AI Agent（第 4 周） | 百炼 Key 仅在服务端；4～5 个只读 Tool；会话隔离；流式输出/重连 | Java AI + 小程序 | AI 回答个体信息有数据库依据；跨用户 session 不泄露；无数据不编造 |
| M4 可选 RAG（第 5 周） | Chroma 仅存审核长文；按 individual_id/species_id 元数据过滤；来源引用；更新/删除索引 | Java AI + 数据人员 | 知识问答显示引用；不同个体不串内容；删除或撤回后不再检索 |
| M5 物种打卡和讨论（第 6～7 周） | 可信 job 发奖、同人同物种同日唯一、名次档位、钱包流水、Redis 排名；当天讨论/审核 | Java + 小程序 + 管理端 | 并发签到只奖一次；同毫秒评论不丢；未签到/跨日拒绝参与 |
| M6 积分商城（第 8 周） | 商品/配额/库存/积分订单同事务，重试幂等，管理端上下架；可选 Redisson 削峰 | Java + 小程序 + 管理端 | 同时抢兑余额/库存不为负，限购无法超额，重复 requestId 不重复扣分 |
| M7 稳定性与展示（第 9～10 周） | 权限审计、故障恢复、API 监控、部署文档、答辩截图和测试报告 | 全体 | 用独立测试数据库从零部署；功能、并发、安全、恢复流程可重复 |
| 条件分支 OPS | 等外部异常识别模型接入后做告警接收、去重、审批、SSE 与辅助分析 | 视觉模型 + 管理端 | Mock 数据与真实设备数据明确标记，不在没有模型时冒称已上线 |

> 如果只有 **2～3 人、每周投入不足 12 小时**，优先完成 M0～M3 的可演示闭环，然后选择 M5 中的每日打卡和基础评论；商城及异常管理后移。RAG 可以只做独立 POC，不必硬塞入首版发布。

## 三、具体工单（建议一张工单对应一个 PR）

### P0：权限、可信性和现有 bug

- [ ] `SEC-01`：`UserController` 不能记录密码；`JwtTokenUserInterceptor` 不能打印完整 Token；摄像头密码不能出现在日志。
- [ ] `SEC-02`：JWT 包含 `subjectType`，员工、游客路由分别鉴权；对 `BaseContext` 增加请求结束清理。
- [ ] `SEC-03`：`POST /visitor/auth/wechat`，微信 code 到服务端交换；测试/生产环境分离。
- [ ] `REC-01`：Java 统一验图、落图、排队调用视觉模型；`recognition_job` 含模型/结果版本。
- [ ] `REC-02`：旧 `/open/recognition-records` 不再发奖，标识为 `UNTRUSTED_LEGACY` 或关闭匿名写。
- [ ] `REC-03`：名称 fallback 必须使用物种限定且唯一；优先使用稳定 `individual.code`。
- [ ] `REC-04`：增加 `unknown/uncertain/failed` 结果和无卡片降级，不得误认。

### P1：能交付给普通用户的核心产品

- [ ] `CARD-01`：`individual.avatar_url/age_source/age_as_of`（需要确认真实表），返回 `animalCard` DTO。
- [ ] `CARD-02`：小程序结果页从“只有预测概率”改为卡片：头像、姓名、物种、年龄描述、可信状态、问答按钮。
- [ ] `AI-01`：AI 会话以 `sessionId+visitorUserId` 绑定；独立 service 访问百炼；限流、超时与敏感词策略。
- [ ] `AI-02`：只读工具 `getCurrentIndividual / getAnimalProfile / listPublicObservations / getMyPoints / listAvailableRewards`；工具参数由服务端复核。
- [ ] `AI-03`：聊天流事件有 `eventId`、`type`、`payload`、`done`、`error`，支持断线后通过 REST 补偿；WS/SSE 传输方式统一状态机。
- [ ] `RAG-01`（可选）：创建 `animal_knowledge_v1` 和 `species_knowledge_v1`；上传仅审核通过内容，不上传原图/精确定位。
- [ ] `RAG-02`（可选）：按 `individualId` 或 `speciesId` 过滤检索，返回来源并尊重“撤回/删除”；禁止跨动物的内容混用。

### P1：打卡、讨论与商城

- [ ] `CHECKIN-01`：`POST /user/checkins` 接收**服务端签发**的 recognitionJobId；后端验证 job 属主、状态、时间、物种、是否已领奖。
- [ ] `CHECKIN-02`：MySQL 唯一 `(visitor_user_id,species_id,biz_date)`；排序、加积分、写账本一笔事务；积分按原 `/docs` 档位执行。
- [ ] `CHECKIN-03`：Redis 排名是可重建投影，数据库失败不能产生“只有 Redis 领过奖”的事实；跨日以上海时区处理。
- [ ] `FEED-01`：每物种每天独立 Feed；发布/读写权限依据当天真实签到校验；图像和文字先审核/过滤。
- [ ] `FEED-02`：`(create_time,id)` 双字段分页；同毫秒和删除评论不漏项/不重复。
- [ ] `MALL-01`：商品可设普通/特价、数量、限购、有效期，服务端定价。
- [ ] `MALL-02`：订单 `requestId` 唯一；`point_wallet` 非负余额扣减、商品库存条件更新、`point_goods_quota` 同事务更新。
- [ ] `MALL-03`：失败重试、退款/撤销的补偿账本；Redis/Redisson 不做账本唯一真实来源。

### P2：展示品质和研究性指标

- [ ] `MODEL-01`：收集按物种分类的混淆矩阵，单独记录 unknown 检测与实际置信度阈值结果。
- [ ] `MODEL-02`：跟踪识别总时延 P50/P95、模型超时/失败率；保存模型版本。
- [ ] `RAG-03`：构建 30～50 题带依据的评测集：错个体、编造年龄、提示词注入、撤回文档、缺资料等。
- [ ] `OPS-01`（条件）：真实边缘行为模型到位后接收告警，AI 仅解释已验证事件。

## 四、重点测试矩阵（建议自动化）

| 编号 | 测试操作 | 必须的结果 |
| --- | --- | --- |
| T01 | 用 CURL 直接对旧开放接口 POST `elephant_name` 和自造 `confidence=100` | 不产生签到资格或积分 |
| T02 | A 用户读取 B 用户识别任务/AI 会话 | 403 或 404，绝不泄露 B 的图片和资料 |
| T03 | 游客 Token 访问员工 `/user/page` 或摄像头密码接口 | 拒绝，员工权限不被游客继承 |
| T04 | 两只同名动物分属不同物种 | 由 `speciesId+code` 正确匹配，匹配不了返回 uncertain |
| T05 | 个体无头像、年龄缺来源 | 默认图/“未知”；AI 不能编造年龄 |
| T06 | 同一游客同一物种同日并发 20 次签到 | 最多一条 `species_checkin`，一笔加分流水 |
| T07 | 不同游客同物种同时签到 100 次 | 排名唯一且连续；档位奖励一致；后台可对账 |
| T08 | 上海时间 23:59:59 和 00:00:01 两次签到 | 正确分属不同 bizDate |
| T09 | Redis 故障但 MySQL 提交成功 | 钱包与签到真实有效，榜单稍后可从库恢复 |
| T10 | 同毫秒 3 条评论，分页 size=1 | 三页全拿到，不遗漏、不重复 |
| T11 | 未当日签到游客尝试发帖、评论与读取限权 Feed | 按需求拒绝；管理员有独立审查权限 |
| T12 | 同一订单 requestId 50 次并发兑换 | 最多一个订单，一次扣分和一次扣库存 |
| T13 | 同一游客不同 requestId 并发绕过限购 | 仍然只允许 `limit_per_user` 数量 |
| T14 | 余额只够兑换一个商品，两个不同商品并发请求 | 最多一个成功，余额不为负 |
| T15 | 库存只有 1，50 个游客同时提交订单 | 最多一个成功；库存不为负 |
| T16 | 模型超时、崩溃或返回异常 JSON | 任务有失败状态与重试/错误提示，不返回假卡片 |
| T17 | Chroma 文档含“忽略系统指令”文本 | LLM 把检索文档视为数据，不执行其中指令；不能调用未授权 Tool |
| T18 | 一个动物个体的 Chroma 文档已撤回 | 重新检索不返回该文档；缓存一并失效 |
| T19 | 模型置信度低于校准阈值但用户手选候选 | 显示“用户确认”，默认不加积分 |
| T20 | 故意上传巨大 Base64、伪装 MIME 的文件 | 拒绝并记录安全事件，不进入模型队列 |

## 五、分工范例（3 人）

- **A：Java 后端与数据**：游客鉴权、识别代理、卡片接口、账本和商城一致性；负责代码审查的安全基线。
- **B：小程序与 Vue 管理端**：微信授权、结果卡片、聊天窗口、签到讨论/商城页面；管理员功能和异常展示。
- **C：AI 与算法/质量**：梳理原 `/predict` 输入输出、类别映射与阈值；百炼 Tool Calling/可选 Chroma；测试自动化和模型评测。

全员共担代码评审与接口契约，不建议 AI 同学自行直接读写订单余额。开发阶段每周至少保留一次集成演示，用 Mock 识别结果串起来；直到具备真实模型、测试库、真实登录环境，才声称完整上线。

## 六、每个 PR 的提交模板

```text
[工单] PR 标题：例如 REC-03 按 species_id + code 关联个体
背景：原逻辑的问题（附源码位置）
变更文件：controller/service/entity/mapper/SQL/小程序
接口/DB：契约变化，需不需要迁移，如何回滚
边界：无识别结果/无授权/超时/失败/重复请求
测试：单元、集成、手工复现命令和截图
安全：是否打印敏感数据，是否改变权限，是否影响积分
演示：成功链路 + 失败链路
```

**先达到 DoD 再勾选完成**：代码审查通过、数据库迁移经评审、可重复测试、未提交生产密钥、记录异常处理，并明确该功能是否已联调真实服务。
