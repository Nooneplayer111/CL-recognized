## 一句话的项目升级路线

**原有大象识别 → 可信的 Java 服务端识别任务 → MySQL 个体卡片 → 百炼只读工具 Agent → 可选 Chroma 动物知识 RAG → 每日物种打卡/讨论 → 安全可对账的积分商城。**

管理端异常行为辅助是额外工作流，必须等真正的边缘识别模型及事件数据接入后再作真实演示。

## 核心原则

1. **权威身份、头像、年龄、积分、订单都来自数据库/业务服务，不由 LLM 或 Chroma 生成。**
2. **大模型不负责看图识别个体。** 小程序上传原图后由受控视觉服务处理，模型产出仅通过 Java 严格映射档案。
3. RAG 用于已审核的观察长文、动物故事与科普知识，优先采用 `individual_id/species_id` 过滤，用户自填评论不可直接作为可信文献。
4. **员工账户不能当游客账户用**，游客和员工的 JWT、路由、数据域分离。小程序匿名上传的预测 JSON 不可直接触发积分。
5. **积分与限购按 MySQL 事务和唯一约束保证**，Redis/Redisson 可加速，但不能替代权威账本。
6. 不公开野生动物精确坐标；识别原图等敏感数据按最小权限和最短必要期限存储。

## 当前可证实、尚未证实的边界

本次读取了实际 ZIP 中的 Java/Vue/微信小程序和 `/docs` 下两个 `.md`。可以定位到现有匿名识别记录写入、旧模型按名称关联个体、员工登录、空打卡页等具体代码。**没有**运行真实 MySQL、Redis、百炼、微信登录、FastAPI 图像模型；ZIP 中也没有实际边缘异常识别算法的可运行服务与必要模型。故接口、数据库迁移和 RAG 示例均标注“建议/草案/POC”，不能据此报告系统已完成升级。

## 开工会需要定下的五件事

1. **积分资格**：仅高可信“个体已识别”可加分，还是高可信“仅物种已识别”也可以？首版建议后者单独定义清晰规则，不凭人工手选得分。
2. **年龄档案**：是出生日期精确计算，还是研究者估计年龄？数据缺失时必须显示未知。
3. **两阶段模型可用性**：是否已经具备物种分类器与每物种个体模型，还是只有当前大象 `/predict`？后者优先“旧接口兼容层”。
4. **讨论审核**：先审后发、自动初筛再人工、公开位置脱敏策略。
5. **商品规则**：限购粒度（永久/每期）、退款操作人、特殊商品并发目标、积分有效期。
